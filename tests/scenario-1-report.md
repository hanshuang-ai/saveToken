## 撤回的解释

1. **“每步约 1.4 秒 hook 开销”没有测量依据。** 总耗时除以旧调用数的差值不能分离 classify、compress、SQLite、模型、网络和工具执行耗时。需要逐次 hook 起止时间与分阶段计时。
2. **“压缩导致更多 API/Bash 调用”尚未证明。** 先去重消息和工具调用，再检查额外操作的目的及对应输出；运行差异本身不足以归因。
3. **“handle 元数据抵消压缩收益”仅是假设。** 需要测量压缩前后模型实际接收的 token，分离元数据、重复消息与原文存储。JSONL 字节增大不能支持此结论，旧称 300-500 字符也未复核。
4. **“Cache read 增加说明前缀匹配被破坏”逻辑不成立。** cache read 是读取缓存的 token，不是 miss 计数。更长上下文或更多请求也可能增加读缓存量；需结合逐请求未缓存输入、缓存写入、读取和可比前缀证据。
5. **“结论不同证明压缩丢失细微信号”证据不足。** 原报告记载对照组倾向 `wecarnavi 内存泄漏 -> LMK`，实验组倾向 `visualizationservice 纹理泄漏`，两者都未独立复核。随机性、工具路径和环境差异也是可能原因；需要原文与压缩输出逐项对照、必要时取回原文，并由独立评审验证结论。

## 修正后的统计规则

- 仅解析 `type: "assistant"` 的 `message.usage`；不累计顶层 usage、user/system/progress/result 记录或嵌套代理摘要中的 usage。
- 以 `(sessionId, message.id)` 去重流式重复块，保留最后的 usage 快照，不累加也不取各字段最大值。有效时间戳用于区分跨文件副本的新旧；缺失或相同时以输入顺序为准。唯一消息数不是实测 API 请求数，不能覆盖未落盘的失败、重试或其他请求。
- 分别统计 `input_tokens`（未缓存输入）、`cache_read_input_tokens`、`cache_creation_input_tokens` 和 `output_tokens`。全输入是前三项之和，全 token 是四项之和；不再把嵌套 cache creation TTL 明细加一遍。
- 缺少或无效的顶层计数明确为 unknown，不假设为零，也不以嵌套明细补全。缺失文件、无 assistant 消息、无法识别消息 ID、JSON 截断、缺少最终 stop_reason、末尾仍停在工具调用或追加用户消息后尚无终止回复，均阻止收益比较。空组不计为零收益。
- 同一组内多轮 resume 指向同一个 JSONL 时只读取一次。读取明确路径旁的 `<session>/subagents/` 中 JSONL（含子目录），与父会话共同按消息身份去重，不再次统计父记录中的代理摘要。此布局之外的代理文件需要明确补充路径，不能全局猜测。
- 仅使用 manifest 指定路径及其会话子代理目录，不搜索全局“最新文件”。路径相对 manifest 目录解析；会话 ID 冲突或两组会话重叠时禁止比较。
- 任一组不完整或 usage 未知时显示收益 unavailable，不跳过该组后计算总体收益。零基线的百分比为 n/a。脚本仅输出各场景比较，不输出选择性排除缺失场景的总体节省值。
- “recorded usage complete”只表示已提供记录满足检查，不证明任务成功、会话文件从未被裁剪或实验归属正确。原编排器使用全局最新文件匹配且未记录可靠完成状态；本次未修改它。当前 manifest 的一个明确路径已确认不存在，因此不能据现有记录重新发布验证后的表格，也未搜索替代会话。
- 原始 token 差值不等于费用差值：不同缓存类别的计费权重及模型价格需另行确认。
